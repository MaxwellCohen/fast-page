Where does inlining CSS start to lose?

The same text-LCP page with 3 KB to 250 KB of CSS, as <style>, <link>, and <style> plus a second copy at the end of the body (what Next.js inlineCss sends: the CSS again in the RSC payload). Each is measured on a cold first load and a repeat visit, where the HTML is no-store like an SSR page and the linked CSS is immutable. For an app with soft navigation, that one full load per session is the only time CSS delivery matters.

On a cold first load, inlining never lost at any size, on any network. The saving is roughly constant, about one request latency: 576 ms on Slow 4G, 171 ms on Fast 4G, 34 ms on Cable (average across sizes; the smallest was 568 ms / 164 ms / 32 ms). A linked stylesheet costs one round trip plus the same bytes, so there is no crossover on first load.

The cost shows up when the CSS would have been cached. On a repeat visit, the inlined CSS is downloaded again at about 5.7 ms per brotli KB on Slow 4G, 1.1 ms per brotli KB on Fast 4G, 1.6 ms per brotli KB on Cable. The break-even depends on how many sessions start with the CSS already in cache.

Duplicating the CSS (Next.js-style) cost at most 8 ms of LCP versus a single inline copy (median across sizes: 0 ms). Brotli's window is larger than the CSS, so the second copy compresses to almost nothing (+2.2 KB at 250 KB), and it sits after the LCP content. That depends on the compressor: at 250 KB the copy adds 70.6 KB with gzip (its 32 KB window can't see the first copy) and 10.5 KB with brotli quality 5 (typical for on-the-fly CDN compression).

Heuristic for frameworks

Let s be the first-visit saving and c(size) the repeat-visit cost. Inlining is better on average when the share of sessions that start with the CSS cached is below s / (s + c). From this data:

  • Slow 4G: s ≈ 576 ms; c ≈ -13 + 5.7 × brotliKB ms (link rate alone predicts 5.6 ms/KB).
  • Fast 4G: s ≈ 171 ms; c ≈ -2 + 1.1 × brotliKB ms (link rate alone predicts 1.0 ms/KB).
  • Cable: s ≈ 34 ms; c ≈ -1 + 1.6 × brotliKB ms (link rate alone predicts 1.6 ms/KB).

So the threshold isn't a fixed byte count. It scales with request latency divided by per-KB transfer time, and with how often your CSS is actually cached (deploy frequency matters: a new hash is a cold load). The "inline wins if returning <" column below gives the break-even share at each size.

For example, on Slow 4G at 50 KB of CSS (13.2 KB brotli), inlining wins unless more than 91% of sessions start with a warm cache.

A practical rule that follows: inline the CSS needed for the first route when it's small, and also emit it as a linked, immutable file so later full loads can use the cache (for example by inlining only when the request has no cookie or marker showing the asset was already fetched).
