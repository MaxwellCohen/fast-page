Inline vs linked CSS

Next.js's experimental.inlineCss swaps every <link rel="stylesheet"> for a <style> tag. The docs say this speeds up FCP and LCP for first-time visitors, with the trade-off that the CSS can't be cached. These pages measure how much it actually changes. They are plain HTML and CSS with no JavaScript.

Summary

Inline

First visit on a high-latency connection

A linked stylesheet is only discovered once the HTML arrives, and then it costs a second round trip. Inlining removes that, so FCP and LCP both move earlier by about one RTT plus the CSS download. Measured with 3 KB of atomic CSS: 160 ms faster LCP on mobile and 432 ms on high-latency 3G, for +1.2 KB of HTML.

Doesn't matter

Low latency, or CSS that isn't render-blocking

On broadband (20 ms RTT) the extra request costs 28 ms, which is within run-to-run noise. CSS placed after the LCP content (for example, a stylesheet for below-the-fold widgets in the body) doesn't affect FCP or LCP either way. Measured LCP difference (link minus inline): 0 ms on mobile and -12 ms on 3G.

Link

Large CSS and more than one page view

With a 250 KB bundle (56.7 KB brotli), inlining still wins on the very first page (160 ms on mobile). Every later page re-downloads the bundle inside its HTML, though, while the linked file comes from cache. On page 2 the linked version is 292 ms faster on mobile and 664 ms faster on 3G.

large-inline → page 2 · large-link → page 2

Rule of thumb: inlining saves about one RTT per first page view and costs the CSS bytes on every page view after it. Inline when the CSS is small enough that re-sending it is cheaper than a round trip (atomic CSS, single landing pages). Link when the bundle is large and visitors view more than one page.

Where exactly is the line? The size sweep measures 3–250 KB of CSS on Slow 4G, Fast 4G and cable, for first and repeat visits, with the raw data as JSON and CSV.

Why

  • A linked stylesheet costs one round trip plus its bytes. The browser only finds the <link> after the HTML arrives, then has to request the file. Inlining saves the round trip but not the bytes.
  • So the gain scales with RTT, not with CSS size. 3 KB or 250 KB, inlining saves about one RTT on a first visit (160 vs 160 ms on mobile). The cost scales with CSS size: the bytes are re-sent on every page view.
  • LCP only improves if the CSS is on its critical path. Chrome blocks rendering only for content after a stylesheet, so CSS placed after the LCP content doesn't delay it, whether inlined or linked. The same is true when the LCP waits on something slower than the CSS, like an image, font, or API response.
  • A long document doesn't hide the cost. Chrome paints progressively, so even a 150 KB article page still waits for the linked stylesheet before its first paint.
  • Caching is where linking wins. Inlined CSS is part of each HTML response. Most sites serve HTML with a short cache lifetime (or none), so the CSS is downloaded on every navigation.

What other performance folks say

Published measurements point the same way as the table above: inlining saves about a round trip on a cold first visit. The caveats below are things these pages don't measure.

  • Barry Pollard (Chrome) and Philip Walton, Optimize Largest Contentful Paint (web.dev, updated 2025). Inlining is "only recommended if your style sheet is small", because inlined CSS can't be cached across page loads. Their preferred fix is to make the stylesheet smaller than the LCP resource: remove unused CSS, defer non-critical CSS, and minify and compress the rest.
  • Barry Pollard, Inlining CSS is not for me (tunetheweb.com, 2015, updated 2022). Inlining cut first paint from 1.271 s to 0.879 s, and cached first paint from 0.428 s to 0.254 s. He still chose not to inline, citing build complexity, CSS repeated on every page, harder debugging, and friction with Content Security Policy.
  • Barry Pollard, Critical resources and the first 14 KB (tunetheweb.com, 2019, updated 2022). Explains the TCP slow-start reasoning behind "render in the first round trip", which the DevTools throttling used here doesn't model. TLS, HTTP/2 setup, and response headers use part of that budget, so treat 14 KB as a rule of thumb, not a limit.
  • Matt Zeunert (DebugBear), Inlining Critical CSS: Does It Make Your Website Faster? (2025). "If you just inline critical CSS you won't see an improvement": the full stylesheet also has to stop blocking rendering. Its listed downsides are larger HTML, no caching across pages, critical CSS that changes with viewport and login state, and layout shifts when the full stylesheet arrives. See also Fix Your LCP Score By Improving Render Delay.
  • Harry Roberts, Critical CSS? Not So Fast! (CSS Wizardry, 2022). The counterpoint. If synchronous JavaScript in the <head> is the bottleneck, inlining changes nothing: in his demo, Start Render was identical with and without critical CSS. The media="print" swap trick can backfire because print stylesheets get the lowest priority (one waited over 12 s). He recommends long-cached, fingerprinted CSS bundles for most existing sites rather than adding critical CSS later.

In Chrome DevTools, check Network → Disable cache, set throttling to Slow 4G, and record a Performance trace of each page in a pair. To reproduce the table: node inline-css/bench/measure.mjs && node inline-css/bench/build.mjs.
